# 振り返り：営業訪問前調査システム

実行日：2026-10-18

## 1. 成果

### 作ったもの

産業廃棄物の処理受託を営業する担当者のために、訪問先3社の事前調査を同時に行い、1社1ファイルの訪問前レポート（.pptx）を自動生成するマルチエージェントシステムを作った。

| 要件 | 実装 |
|---|---|
| カスタムサブエージェント2つ以上 | `prospect-researcher`（調査）、`waste-analyst`（廃棄物分析）、`report-writer`（執筆・修正）、`reviewer`（レビュー）の4つ |
| 自作 Skill 1つ以上 | `prospect-research`（調査観点・情報源・ひな形）、`waste-estimation`（廃棄物区分・業種との対応表・確度ルール・提案サービス）、`sales-report-pptx`（8枚構成の規約・生成スクリプト）の3つ |
| Agent ツールによる並列処理 | 調査・廃棄物分析・執筆の3工程で、3社分を同じメッセージ内で同時に起動した。修正工程も3社同時に起動した |
| 最終出力にスライド | `output/訪問前レポート_{社名}_20261018.pptx` を3ファイル（各8枚）生成した |

### 実行結果

入力した3社（株式会社虎屋、株式会社マースエンジニアリング、アイリスオーヤマ株式会社）について、手順どおり最後まで動作した。

| 社名 | 訪問拠点（特定結果） | 推定した廃棄物 | 最有力の提案 |
|---|---|---|---|
| 虎屋 | 御殿場工場（羊羹・餡の製造） | 9種類 | 小豆の皮の有価売却は残し、それ以外の食品残さ・包装材・検査廃液を一括受託 |
| マースエンジニアリング | 東富士工場（パチンコホール向け電子機器） | 10種類 | 2026-12 完了予定の設備導入に合わせたスポット回収から一括受託へつなげる |
| アイリスオーヤマ | 富士小山工場（PETボトル飲料水） | 10種類 | 製造ライン・物流倉庫・社員食堂の一括受託と、PETくずのリサイクル |

各工程の所要時間（サブエージェントごと）は次のとおりである。

| 工程 | 3社それぞれの所要時間 | 並列での所要時間 | 逐次なら |
|---|---|---|---|
| 調査 | 約3.3分／約4.0分／約5.6分 | 約5.6分 | 約12.9分 |
| 廃棄物分析 | 約1.8分／約1.9分／約1.9分 | 約1.9分 | 約5.7分 |
| 執筆 | 約1.2分／約1.1分／約1.3分 | 約1.3分 | 約3.6分 |
| レビュー（3社まとめて） | 約3.4分 | — | — |
| 修正 | 約0.6分／約1.0分／約0.8分 | 約1.0分 | 約2.3分 |

並列にした4工程は、逐次なら合計約24.5分かかるところを約9.8分で終えた。

レビューでは3社とも「要修正」が1件ずつ見つかり、1回の修正ですべて反映した。価格の記載と法令違反の断定はなかった。

## 2. 工夫した点

- **工程ごとに役割を分けた。** 調査（事実を集める）、廃棄物分析（推定する）、執筆（伝える）、レビュー（確かめる）を別のエージェントにした。これにより、事実と推定が混ざらない。レビューでも、誤りの原因が調査メモ・分析・スライドのどこにあるかを特定できた。
- **並列と逐次を依存関係で決めた。** 同じ工程の3社分は互いに依存せず出力ファイルも別なので並列にした。工程どうしは前の出力を使うので逐次にした。各エージェントの書き込み先を担当ファイルだけに限ったので、並列でもファイルが競合しない。
- **推定の確度を3段階で書き分けた。** 廃棄物の推定を「公表情報あり」「業種から推定」「要ヒアリング」に分けた。スライドでも色分けしたので、営業担当者は訪問時に何を確かめればよいかが一目で分かる。
- **業界の知識を Skill にまとめた。** 産業廃棄物20種類の区分、業種限定の区分（動植物性残さなど）、特別管理産業廃棄物、事業系一般廃棄物との区別を `waste-estimation` に入れた。その結果、3社とも区分を正しく扱えた（レビューで確認済み）。
- **禁止事項をルールにした。** 価格・処理単価を書かない、相手企業の法令違反を断定しない、を CLAUDE.md と各エージェントに書いた。実際に、PCB や蛍光管は「確認は済んでいるか」と聞く形で書かれた。
- **見た目の統一をスクリプトに任せた。** 執筆担当は JSON 原稿だけを書き、デザインは `build_pptx.py` で統一した。3社のレポートは同じ構成・同じ見た目になり、修正は原稿を直して作り直すだけで済んだ。
- **修正は1回までにした。** レビューと修正を無限に繰り返さないよう、修正は1回までとし、残った指摘はユーザーに報告するルールにした。

## 3. 改善したい点

- **修正の範囲がスライドにしか届かない。** マースエンジニアリングでは、スライドの件数を 0／2／8 に直したが、分析ファイルは 0／3／7 のまま食い違っている。原因が分析にある指摘は、修正工程で `waste-analyst` も起動できるようにしたい。
- **スライドで事実が増えた。** PCB の処分期限など、調査メモにない事実が分析・スライドの段階で加わり、出典がなかった。法定期限のような一般的な情報も、調査メモか Skill に出典つきで持たせたい。
- **確度の条件がスライドで落ちやすい。** 要修正の3件はどれも、調査メモの「不明」「2021年時点」という条件が、要約したときに抜けたものだった。執筆担当のルールに「条件や時点は短くしても消さない」を明記したい。
- **公表情報が少ない企業では精度が上がらない。** 3社とも「公表情報あり」は0件だった。また、公式サイトの本文を取得できない場合（アイリスオーヤマは 403 だった）は、検索結果の抜粋に頼ることになった。多量排出事業者の処理計画（自治体の公表資料）のように、取得しにくい情報源の扱い方を Skill に足したい。
- **pptx の見た目を確認していない。** 生成スクリプトはエラーなく動いたが、文字のはみ出しは誰も目視で確認していない。pptx を画像にして確認する工程を、執筆またはレビューに入れたい。
- **3社以外の件数に対応していない。** 今は3社固定である。1〜5社など可変にできれば、実際の営業でも使いやすい。

## 4. 学んだこと

- **並列化の効果は、一番遅い1件で決まる。** 調査は社によって約3.3分〜約5.6分と差があり、並列でも全体は最も遅い社に合わせて待つことになる。それでも逐次の半分以下の時間で終わり、並列化の効果ははっきり出た。
- **役割を分けると、レビューの指摘が具体的になる。** 調査メモ・分析・原稿が別ファイルに残るので、レビュー担当は「スライドのこの記述は調査メモの条件を落としている」「原因は分析の #2」と、根拠と原因の場所を示して指摘できた。
- **エージェントには「書いてはいけないこと」を明確に伝える必要がある。** 担当ファイル以外に書かない、調査メモにない事実を加えない、と決めておいたので、執筆担当は焼菓子の情報を自分の判断で足さず、理由を報告してきた。ルールがあることで、エージェントの判断が予測しやすくなった。
- **Skill は、エージェントの判断をそろえる仕組みとして効く。** 同じ Skill を使う3つのエージェントが、別々の企業を調べても同じひな形・同じ確度ルールで書いた。そのため、3社を同じ基準でレビューできた。
- **一般的な知識こそ出典の管理が要る。** モデルが「知っている」情報（法定期限など）は自然に原稿に入ってくる。営業資料の正確さを保つには、そうした情報にも出典を付ける仕組みが必要だと分かった。
